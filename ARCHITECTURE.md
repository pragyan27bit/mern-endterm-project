# Technical Architecture & Engineering Notes

## Services

A single Node.js process uses Express to expose `/api` and serve Vite's production build. React is a client-side application with React state and a shared `api` wrapper. There is no cross-domain cookie sharing and no separate frontend host.

## Model overview

**User**: `name`, unique `email`, `passwordHash`, `dailyCapacity`, `isDemo`.

**Task**: `owner`, `title`, `course`, `description`, `dueDate`, `priority`, `estimateMinutes`, `spentMinutes`, `status`, nullable `dependsOn` (a task reference), `completedAt`.

**Focus**: `owner`, `task`, `minutes`, `method`, `day`.

**Plan**: unique `owner`, `startDate`, `capacity`, `blocks[]` (task, date, minutes), `conflicts[]` (task, unscheduled minutes, explanation), timestamp.

Indexes include unique user email, task `(owner,dueDate)`, focus `(owner,day)`, and unique plan owner.

## Authorization

1. Signup/login hashes/verifies passwords using bcrypt.
2. JWT is signed with the server secret and set in an HTTP-only cookie with `SameSite=Lax`. Production cookies are marked `Secure`.
3. `requireAuth` checks the token signature and resolves the user.
4. Task, focus, profile and plan endpoints always scope database operations to `req.user._id`.
5. Prerequisite task references are validated to belong to the same user; self-references and cycles are disallowed.

## Scheduling algorithm

Let `M = max(0, estimateMinutes - spentMinutes)`. Compute a deterministic heuristic:

`score = priorityWeight + deadlineUrgency + remainingWorkPressure`

Priority weights: high 30, medium 15, low 0. Deadline urgency rises as deadlines approach; overdue tasks are reported as conflicts because their due dates have already passed. Work pressure scales unfinished minutes by time until deadline.

For each of the next seven calendar days:

1. Set remaining day capacity to user preference (30–720 minutes, steps of 15).
2. Filter unfinished and unblocked tasks that have not passed their due date.
3. Choose the highest-scoring task; allocate `min(dayRemaining, taskRemaining, 90 minutes)`.
4. Repeat until day capacity is used or no eligible work remains.
5. Report unallocated work and blocked tasks, not imaginary extra calendar hours.

The engine is pure, unit-tested, and runs on in-memory task objects read from MongoDB. Persisting the result is handled separately by the route.

### Time complexity

For `T` tasks, seven days, and `B` emitted blocks, the engine's straightforward repeated candidate sorting costs approximately `O(7 * B * T log T)` in the worst case. This favors clarity and testability over sophisticated optimization for small student workloads.

## Client state and lifecycle

- Initial page load calls `/api/auth/me` and loads authenticated tasks, plan, and insights in parallel.
- Write operations await the server and refresh all three datasets before showing success.
- The URL hash remembers the selected section; pages are not separate servers.
- The timer runs in the page only; sending `/api/focus` creates persisted sessions.
- The planner is explicitly regenerated by the user after data changes, avoiding surprising automatic plan overwrites.

## Constraints and tradeoffs

- The project demonstrates a useful single-user workflow, not class administration or team roles.
- Multiple sessions can be logged against one task; estimate and logged minutes are deliberately separate from completion status.
- Full event sourcing, password recovery, OAuth, transactional multi-document writes, and reminders are deferred to keep the five principal flows reliable.

## Testing strategy

The included Node test suite tests key planner invariants: capacity, deadline, prerequisites, completed prerequisites, logged effort, priority, date rollovers, and invalid input. GitHub Actions additionally checks backend syntax and attempts a production frontend build. Manual end-to-end deployment testing is necessary after configuring MongoDB Atlas and hosting.
